# Company and security master specification

## Entities and relationships

- **Company** is the issuer or underlying legal/business entity. It has no ticker uniqueness rule and may issue multiple securities.
- **Security** is an instrument or share class issued by a company. It contains issuer and instrument-level information such as security type, with no ticker, exchange, currency, or listing lifecycle fields.
- **Exchange** is a stable venue reference, independent of company symbols. `exchange_code` is the unique natural/stable code; the integer `exchange_id` is the local database key. Region, IANA timezone, country, and trading currency are reference data and are not hardcoded into Domain rules.
- **SecurityIdentifier** records an explicit identifier type and a text value. `resolve_identifier_scope` is the single source of scope rules: ISIN is globally unique even if an exchange annotation is present; `TICKER`, `TRADING_CODE`, and `EXCHANGE_CODE` require an Exchange and are unique within that Exchange; other types are global without an Exchange and exchange-scoped when one is supplied. Validity dates preserve identifier changes. Identifiers are not mandatory or assumed to exist for every security.
- **Listing** joins a Security to an Exchange with a ticker, trading currency, listing date, optional delisting date, and current status. A security may have listings on multiple exchanges. Listing status changes are retained as append-only `ListingStatusEvent` rows.

The schema accommodates Japan (for example `XTKS`, `Asia/Tokyo`, `JPY`), the United States (`XNYS`/`XNAS`, `America/New_York`, `USD`), Mainland China (`XSHG`/`XSHE`, `Asia/Shanghai`, `CNY`), and Hong Kong (`XHKG`, `Asia/Hong_Kong`, `HKD`). Canonical MICs follow [ISO 10383](https://www.iso.org/standard/61067.html). These are suggested reference codes, not a closed enum; callers can register other venues without changing Domain code.

## Effective dates and integrity

Listing and identifier date ranges are inclusive. A delisting date must be on or after the listing date. A `delisted` Listing requires a delisting date; active or suspended listings do not have one. A newly registered Listing must start as `active`; its initial active event takes effect on the listing date. Suspension and delisting can only be recorded as later events with their supplied effective dates. Status events must move forward in time, and delisted listings are terminal. Transition updates and their status event insert run in the caller-owned database transaction. One Security can have multiple Listings, including on multiple Exchanges. A different Security may reuse a ticker on the same Exchange after the earlier inclusive listing interval ends.

Identifier reuse is scoped by identifier type and the canonical scope resolver. Application checks reject overlapping validity periods, including global ISIN reuse across rows with different `exchange_id` values. Listing ticker reuse is scoped by Exchange and checked for overlapping listing/delisting dates. Database indexes reject exact-start duplicates in the stored scope (global rows with no exchange and exchange-scoped rows); they do not enforce global ISIN uniqueness across exchange annotations or arbitrary interval overlap. Those checks are Application-level.

## Industry exposures

Each company exposure has a Decimal revenue share in `[0, 1]`. `RegisterCompanyIndustryExposure` and `UpdateCompanyIndustryExposure` load the complete company exposure set, apply the shared `validate_company_exposures` sweep, and persist only after aggregate validation passes. Non-overlapping intervals may independently have shares totaling up to 100%; every point in overlapping intervals must total at most 100%.

## Transaction and migration policy

Use cases flush through Domain repository interfaces and do not commit. The caller owns transaction boundaries so persistence failures roll back the aggregate operation. For SQLite check-then-insert writes, use the Infrastructure `transaction(session_factory)` helper, which starts `BEGIN IMMEDIATE` to reserve the single SQLite writer before validation reads. Raw `Session.begin()` transactions do not provide this serialization guarantee; callers must handle lock/busy errors and retry the entire unit of work. Application rules stay in use cases. A PostgreSQL adapter can strengthen serialization with transaction-scoped advisory locks keyed by global identifier / exchange+ticker, `SELECT FOR UPDATE` on the Company row for exposure changes, and range exclusion constraints for listing and identifier intervals. Exposure share totals still require a Company-scoped lock or serializable transaction because their sum is an aggregate invariant.

Migration `0004_security_listing_normalization` preserves Security primary keys, maps recognized legacy exchange codes into Exchange rows, and moves available legacy ticker/currency/listing dates into Listing plus initial status events. It removes the ticker/exchange uniqueness from Security. Unknown exchange codes, missing listing dates, ambiguous inactive rows, and conflicting normalized listing keys are retained in `legacy_listing_reconciliation` with their original fields and a reason. No timezone, currency, or Exchange record is invented for unknown venue codes. Migration initialization remains idempotent through Alembic's version table and its backfill checks existing natural listing/event keys before insertion. No external security-master or exchange discovery provider is included.
